Несколько ресурсов в одной заявке

Часть 1. Что умеет редакция 2.1

Многоресурсная заявка в 1С:Документооборот 2.1

Разбор по пунктам

1. Табличная часть в карточке внутреннего документа. Штатно — нет. Механизм «Дополнительные реквизиты и сведения» (из БСП) даёт только одиночные значения: строка, число, дата, булево, ссылка на справочник, дополнительное значение. Табличных доп. реквизитов в 2.1 не существует; максимум «многострочного» — реквизит типа Строка с многострочным вводом, то есть неструктурированный текст, к строкам которого процесс обратиться не может. Все решения «табличная часть из доп. реквизитов» на Инфостарте — это расширения с кодом (https://infostart.ru/1c/articles/1059267/" target="_blank" rel="noopener">публикация прямо для ДО 2.1). Аналогичное расширение продаётся https://infostart.ru/marketplace/1878105/" target="_blank" rel="noopener">и для 3.0 — значит, штатно нет и там.

2. Построчное согласование. Нет. Процесс «Согласование» адресуется предмету целиком: результат — «Согласовано» / «Не согласовано» / «Согласовано с замечаниями», фиксируется в листе согласования по участникам, а не по строкам данных. Механизма «результат по строке документа» в 2.1 нет и подтверждения его существования в 3.0 я не нашёл. Построчное согласование встречается только в сторонних подсистемах (https://infostart.ru/1c/tools/544937/" target="_blank" rel="noopener">пример) — это доработка.

3. Подчинённые документы. Есть — механизм «Связи документов»: типы связей настраиваются пользователем в НСИ (обязательные/необязательные, единичные/множественные, с автоматической обратной связью), программист не нужен (https://dokumentooborot24.ru/poleznosti/svyazi-i-czepochki-v-sisteme-1s-dokumentooborot/" target="_blank" rel="noopener">обзор). Создать из одной заявки пять дочерних вручную и связать их — штатно. Автоматическое создание пачки связанных документов по настройке в 2.1 штатно не подтверждается (на Инфостарте это https://infostart.ru/1c/tools/1001554/" target="_blank" rel="noopener">отдельное расширение); настройки автосоздания связей описаны уже для https://www.doc-lvv.ru/nastrojka-sozdaniya-svyazej-mezhdu-dokumentami-1s-dokumentooborot-3-0-19-29" target="_blank" rel="noopener">3.0.19.

4. Ветвление по числу строк. Нет. Комплексный процесс — «набор заранее запланированных действий, стартующих в настроенном порядке и при определённых условиях»; схема проектируется списком действий или графически, ветвление задаётся условиями маршрутизации (конструктор или встроенный язык). Число веток фиксируется при проектировании схемы; динамического размножения N веток по количеству записей нет (https://its.1c.ru/db/doccorp21/content/773/hdoc" target="_blank" rel="noopener">ИТС, гл. 8).

5. Состояние при частичном результате. Реквизит «Состояние» внутреннего документа принимает одно значение из предопределённого набора и меняется процессами автоматически. «Два из пяти» штатно показать нечем, кроме текстового/перечислимого доп. реквизита, который кто-то обновляет руками. Косвенно — через список связанных дочерних заявок, где у каждой своё состояние.

Что появилось только в 3.0 (и чего всё равно нет)

Появилось: настройки обработки в карточке вида документа вместо комплексных процессов; единая вкладка «Обработка»; схемы без исполнителей; «замок» на обязательных участниках; правила обработки по виду/тематике/организации/подразделению (https://is1c.ru/about/pc/article/nastroyka-biznes-protsessa-v-1s-dokumentooborot-3-0-i-1s-dokumentooborot-2-1/" target="_blank" rel="noopener">сравнение 2.1 и 3.0); настройки создания связей 3.0.19. Не появилось и в 3.0: табличные доп. реквизиты и построчное согласование.

Как делают на практике

  1. «Одна заявка — один ресурс» + документ-основание (рабочая модель). Сотрудник создаёт заявку-шапку на приём, из неё по связям — 5 дочерних заявок, у каждой свой владелец, свой срок и своё состояние. Отказ по одной не блокирует остальные, отзыв — по каждой отдельно.
  2. Многострочная заявка текстом + согласование целиком (грубая). Перечень ресурсов в многострочном реквизите, в процесс включены все владельцы; любое «Не согласовано» возвращает всю заявку на доработку. Годится, если отказы редки.
  3. Табличная часть + построчные визы — только через расширение и собственный регистр результатов. Это проект разработки, не настройка.

Вывод

Многострочная заявка с построчным согласованием в редакции 2.1 без доработки невозможна: нет табличной части в карточке, нет результата по строке и нет динамического ветвления по количеству записей. Штатная замена — модель «одна заявка на один ресурс» плюс заявка-основание, связанная типом связи «главный — подчинённые». Это даёт корректные раздельные итоги, сроки и отзывы, а «два из пяти согласовано» читается из списка связанных документов. Переход на 3.0 проблему построчного согласования не решает.

Часть 2. Модели и решение

Короткий ответ

В 2.1 многострочная заявка с построчным согласованием невозможна без доработки: нет табличной части, нет результата по строке, нет динамического ветвления. Берём модель А+В: одна заявка = один ресурс, а для «пачки» делаем заявку-основание и связываем с ней дочерние заявки штатным механизмом связей. Согласование, письма, роль контролёра и страница статуса остаются как есть — меняется только уровень, на котором считается «заявка». Позже, когда наберётся статистика по должностям, поверх этого достраивается Г как ускоритель, а не как замена.

Рекомендация

Берём В с опорой на А: заявка-основание + дочерние заявки «одна заявка — один ресурс».

Почему именно её:

  • всё держится на штатных механизмах — доп. реквизиты, связи документов, обычное согласование документа целиком;
  • частичный результат («два из пяти») читается сам собой — из списка связанных заявок, где у каждой своё состояние;
  • отзыв доступа, срок, продление живут на своём уровне: у каждого ресурса свой срок, а не общий на заявку;
  • отказ по одному ресурсу не откатывает всю заявку на доработку.

Чем платим честно:

  1. Ручным созданием дочерних заявок. Автоматически они не появятся. Это 3–5 карточек на приём сотрудника; ускоряется копированием карточки и типовыми наборами (модель Г).
  2. Ростом числа документов. Вместо 200 заявок в год станет 600–700. Это влияет на отчётность и на восприятие («стало больше бумаги»), хотя работы столько же.
  3. Отсутствием единого статуса у шапки. Состояние заявки-основания не покажет «частично» — оно живёт в дочерних. Компенсируется страницей статуса.

Что делать с уже работающим процессом

Не трогать:

  • шаблон процесса согласования — он адресуется документу целиком, это ровно то, что нужно дочерней заявке;
  • готовые письма — они и так про один ресурс, текст менять не надо;
  • роль контролёра — сохраняется, просто контролёр теперь смотрит и на шапку тоже;
  • состав доп. реквизитов заявки (ресурс, тип доступа, срок) — остаётся один-к-одному.

Изменить:

  1. [НАСТРОЙКА] Завести вид документа «Заявка-основание на доступы» (или отдельный доп. реквизит-признак у существующего вида — что проще администратору). У шапки: сотрудник, событие (приём / перевод / расширение прав), основание, срок.
  2. [НАСТРОЙКА] В НСИ настроить тип связи «главный — подчинённые», множественную, с автоматической обратной связью, между заявкой-основанием и заявками на доступ.
  3. [КОРОБКА] Создание дочерних: заявитель создаёт заявку на ресурс и вручную указывает связь с основанием. Копирование первой карточки ускоряет ввод остальных.
  4. [НАСТРОЙКА] Правило: шапка закрывается только когда закрыты все дочерние. Контролёр проверяет это по вкладке связанных документов.
  5. [НАСТРОЙКА] Нумерация: в шапке видно, сколько ресурсов заявлено — доп. реквизит числом, заполняет заявитель. Расхождение «заявлено 5, создано 3» ловит контролёр.
  6. [ДОРАБОТКА, потом] Автосоздание дочерних по выбранному типовому набору (модель Г). Только если объём оправдает: в 2.1 это расширение.

Что менять на странице статуса

Пилот сейчас показывает один ресурс. Под модель В он становится страницей заявки-основания со списком.

  • Шапка страницы: сотрудник, событие, дата подачи, номер заявки-основания, ФИО контролёра. Добавить сводную строку «Согласовано N из M» — M берётся из доп. реквизита «Заявлено ресурсов», N считается по дочерним со состоянием «Согласовано».
  • Вместо одного блока ресурса — таблица строк, по одной на дочернюю заявку. Поля в строке: Ресурс | Тип доступа | Владелец ресурса (кто согласует) | Состояние | Срок доступа (до) | Дата решения | Номер дочерней заявки.
  • Состояние — то же, что у дочернего документа, не выдуманное: в работе / согласовано / не согласовано / отозвано. Никакого «частично» на уровне строки не бывает — «частично» это и есть сама таблица.
  • Отдельная строка «Итог» внизу: пока хоть одна строка в работе — «Заявка в работе»; все закрыты — «Заявка закрыта», с расшифровкой «согласовано N, отказано K».
  • Сроки остаются построчными, общего срока у страницы нет. Если у ресурсов сроки разные — это видно, и это правильно.
  • Ссылку/QR-код на страницу давать с заявки-основания, а не с дочерней: заявитель хочет видеть картину целиком.

Побочные эффекты, о которых забывают

  • Отчётность. Считать надо строки (дочерние заявки), а не заявки. «Подано 200 заявок» и «выдано 640 доступов» — разные числа; договоритесь заранее, какое из них идёт в отчёт, иначе цифры за прошлый год перестанут сравниваться с новыми.
  • Отзыв доступа. Сроки у ресурсов разные, значит отзыв — по каждой дочерней заявке отдельно. Общего «отозвать всё по заявке» не будет; при увольнении нужен обратный ход — открыть заявку-основание и пройти по всем связанным.
  • Частичный отказ. Отказ по одному ресурсу больше не возвращает всю пачку на доработку — это плюс, но требует правила: контролёр обязан проверить, не блокирует ли отказанный ресурс работу с согласованными (нет смысла давать доступ к папке, если отказали в самой системе).
  • Повторная подача на «недоданное». Новая дочерняя заявка на тот же ресурс с той же шапкой, а не переоткрытие старой. Иначе история отказа затирается и непонятно, почему в первый раз не дали.
  • Дубли. Ничто не мешает подать две заявки на один ресурс одному человеку. Проверка — на контролёре, автоматической в 2.1 нет.
  • Восприятие объёма. Руководство увидит рост числа документов втрое. Предупредите заранее, иначе это прочтут как «процесс усложнили».
  • Архивное хранение. Решайте сразу, что считается единицей хранения — основание с приложенными дочерними или каждая заявка отдельно. Переигрывать через год дорого.
